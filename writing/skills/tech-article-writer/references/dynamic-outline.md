# 动态大纲与递归规划

> 设计参考：`principia-ai/WriteHERE` 的递归任务分解、依赖图和局部重规划。

## 模式选择

默认使用黄金五段式。满足任一条件时建议切换动态模式：

- 主题横跨 3 个以上子系统或技术层次。
- 需要比较多种方案并说明权衡。
- 用户要求深度长文、系列文章或 5000 字以上内容。
- 各章节存在明显前置依赖，固定平铺结构会损失逻辑。

用户可直接说“使用动态大纲”或“使用黄金五段式”。

## 大纲节点

使用 2-3 层树，每个节点包含：

```yaml
id: concept-runtime
parent: core-concepts
heading: 运行时模型
summary: 用两句话说明本节要回答什么，以及结论如何连接下一节。
estimated_words: 600
content_type: concept
source_cards: [1, 3]
depends_on: [concept-basics]
status: planned
```

`content_type` 取值：

- `concept`：概念与边界
- `example`：代码或操作演示
- `analysis`：原因、机制、权衡
- `comparison`：方案对比
- `case_study`：真实案例或复盘

根节点仍映射黄金五段式：场景引入、概念引出、深度解析、案例实践、总结升华。复杂度通过子节点递归展开，不破坏技能原有叙事风格。

## 骨架优先

1. 只生成大纲树及每个叶节点的 1-2 句摘要。
2. 标注预计字数、内容类型、依赖和素材卡。
3. 让用户确认方向；若用户已明确要求直接完成，可自行检查后继续。
4. 按依赖顺序展开叶节点，不按文件中的偶然顺序机械写作。
5. 每展开一节，检查它是否兑现摘要中的承诺。

## 依赖图

将节点视为有向无环图：

- `depends_on` 指向理解本节点所需的前置节点。
- 禁止循环依赖；发现循环时合并节点或重新定义边界。
- 一个节点只承担一种主要内容类型，过重时继续拆分。
- 检索、推理、写作是不同任务；素材不足时先补调研，不直接扩写空话。

## 局部重规划

用户修改某节时，先做影响分析：

- **直接节点**：内容目标或结论被修改，重新生成。
- **依赖可达节点**：检查术语、数据、前提与结论一致性，只做必要微调。
- **无关节点**：保持原文，不重新生成。

执行顺序：

1. 修改前创建版本快照。
2. 定位用户要求对应的节点。
3. 沿 `depends_on` 的正向与反向边找受影响节点。
4. 向用户列出“重写 / 一致性检查 / 跳过”三组。
5. 只处理前两组。
6. 输出 diff 摘要并运行质量检查。

可用脚本做标题级初筛：

```bash
python scripts/version_manager.py \
  --action smart-edit \
  --article-file article.md \
  --edit-description "重写缓存失效部分，补充多租户场景"
```
